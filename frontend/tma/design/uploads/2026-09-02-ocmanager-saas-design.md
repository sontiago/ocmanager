## 1. Что строим

Платформа, которая превращает сервер с ocserv в продаваемый VPN-сервис: клиент покупает
подписку в Telegram Mini App, получает ключ автоматически, продлевается без участия человека,
а владелец сервера управляет всем из админ-панели.

Продукт имеет два применения из одного кода:

1. **Собственный сервис владельца** — своя нода, свои клиенты, свои деньги.
2. **Коробка на продажу** — покупатель разворачивает полный стек у себя, подключает свои
   платёжные реквизиты и своего бота, и либо пользуется VPN сам, либо продаёт доступ.

Мультитенантности нет. Каждая инсталляция полностью независима — это осознанное решение,
которое убирает изоляцию данных, двухуровневый биллинг и SLA из области задач.

### Цели

- Клиент проходит путь «увидел тариф → оплатил → подключился» без единого действия админа.
- Продление подписки не требует действий ни от клиента, ни от админа, ни перевыпуска ключей.
- Владелец видит состояние сервиса и потребление трафика по каждому клиенту и устройству.
- Инсталляция разворачивается человеком, умеющим в SSH и Docker, без чтения исходников.

### Не входит в область задач

- Мультитенантность и реселлерские кабинеты.
- Автопровижининг нод у облачных провайдеров (Terraform, API хостеров).
- Собственные VPN-клиенты под платформы — используются штатные AnyConnect/OpenConnect.
- Бухгалтерия, чеки по 54-ФЗ, работа с юрлицами.

## 2. Исходный контекст

### 2.1. Что уже есть

Каталог проекта пуст — это гринфилд. Два приложенных прототипа не являются основой, но
дают проверенные приёмы работы с ocserv.

**`openconnect-manager` (FastAPI + Jinja + HTMX + SSE).** Один админ из `.env` (bcrypt-хеш),
сессия в подписанной cookie, CSRF на всех POST. Управление через реестр разрешённых действий
`ACTIONS` — произвольная команда невозможна по построению. `docker exec <container> occtl ...`,
`systemctl <action> <unit>`, `docker compose up/down/restart`. Все вызовы — `subprocess` со
списком аргументов, без `shell=True`. Валидация ввода `ocuser` регулярками. SSE для живых
логов и статуса. Слушает только `127.0.0.1`, доступ по SSH-туннелю. Интерактивный shell
намеренно не выведен в веб.

**Приёмы, которые переносим:** реестр разрешённых действий вместо параметризованных команд;
имена контейнера/юнита только из конфига; `subprocess` со списком аргументов; корректное
закрытие дочернего процесса при обрыве SSE (`try/finally` вокруг `await`); loopback-биндинг
админки.

**`ocserv-manager` (Flask + SQLite + vanilla JS).** Админы в БД, `vpn_users`, `audit_log`,
`traffic_stats` с дельтами каждые 5 минут и агрегацией по дням, очистка старых сэмплов.
Парсеры вывода `occtl`. Скачивание `.p12`, отзыв сертификата с обновлением CRL, кик сессий,
чёрный список, DNAT-настройка, метрики хоста, IP-guard по подсетям.

**Приёмы, которые переносим:** дельтовая модель учёта трафика с суточной агрегацией и
ретеншном; журнал аудита; парсинг `occtl` как отдельный слой.

**Почему не достраиваем прототипы:** SQLite не выдерживает конкурентных вебхуков вместе с
фоновым сбором статистики; синхронный Flask плохо совмещает SSE, вебхуки и планировщик; в
коде нет ни одной абстракции, в которую встраивается биллинг. Достройка привела бы к
переписыванию через месяц, но уже с миграцией боевых данных.

### 2.2. Анализ референсов

**`github.com/mmtaee/ocserv-dashboard`** (Go + Vue, MIT, ~267 звёзд). Даёт: группы ocserv с
синхронизацией `/etc/ocserv/groups/*`, лимиты трафика в ГБ и месячные квоты, сроки действия
аккаунтов с автодеактивацией, генерацию и импорт `.p12`, синхронизацию `ocpasswd` с БД,
staff-аккаунты с изоляцией «каждый видит только своих пользователей», журнал действий
администраторов, live-логи, real-time RX/TX, i18n на шести языках, страницу самообслуживания
клиента, Telegram-бот с привязкой аккаунтов, пакетами, заявками на продление, загрузкой
квитанций и оповещениями о низком трафике.

**Habr, статья про `ocservice`** (набор bash-скриптов, без Docker и БД). Даёт: три режима
авторизации (cert / plain / both), PKI на easy-rsa 3.x, отзыв сертификата через
`easyrsa revoke` с обновлением CRL, чтение CRL сервером напрямую из `pki/crl.pem`, срок
действия сертификата как параметр выпуска, лимит одновременных подключений через
`config-per-user`, бан-поинты и их сброс, кик пользователей, точечные права через
`/etc/sudoers.d/`, определение режима камуфляжа из `ocserv.conf` и подстановку секретного
токена в URL шлюза, экспорт `.p12` с паролем.

Полный каталог функций, извлечённых из обоих источников, — в приложении A.

| Вопрос | Решение |

| Модель | B2C, свои серверы; плюс продажа полной инсталляции «под ключ» |

| Trial | Да, N дней / M ГБ, один на `telegram_id` |
| Истечение подписки | Жёсткое отключение сразу |
| Продление | Бесшовное по вебхуку, без перевыпуска ключей |
| Стек | Python: FastAPI + PostgreSQL + Redis + React (TMA) + aiogram (бот) |
| Установка | `docker compose` + `.env`, целевой пользователь — полутехнарь |
| Размещение | ocserv в Docker, панель рядом на том же хосте |
| Публикация | Наружу только TMA; админка на loopback, доступ по SSH-туннелю |
| Обязательно | Камуфляж/обход блокировок, алерты админу в Telegram, i18n ru/en с первого дня |
| Админка | Статистика трафика по пользователям и устройствам |

## 4. Архитектура

Модульный монолит на FastAPI плюс фоновый воркер, всё в одной compose-стеке.
Микросервисы отвергнуты: при одной ноде они дают четыре деплоя и распределённые сбои
при нулевой выгоде, а для «коробки полутехнаря» ещё и увеличивают поверхность поддержки.

```
┌─ Хост (одна docker compose стека) ───────────────────────────┐
│                                                               │
│  nginx stream (:443, ssl_preread по SNI)                     │
│      ├── vpn.example.com  ──────────►  ocserv (камуфляж)     │
│      └── app.example.com  ──────────►  http-прокси           │
│                                              │                │
│  ┌───────────────────────────────────────────▼─────────────┐ │
│  │  api-public  (uvicorn, доступен через прокси)            │ │
│  │   /tma/*        — Mini App API (auth по initData)        │ │
│  │   /webhooks/*   — Tribute, Stars, крипта                 │ │
│  │   /internal/*   — приём данных от disconnect-script       │ │
│  │                   (только из docker-сети ocserv)          │ │
│  ├──────────────────────────────────────────────────────────┤ │
│  │  api-admin   (отдельный процесс, bind 127.0.0.1:8080)    │ │
│  │   /admin/*      — админ-API + UI                          │ │
│  └───────┬─────────────────────────────┬────────────────────┘ │
│          │                             │                      │
│  ┌───────▼────────┐          ┌─────────▼─────────┐           │
│  │  Postgres      │          │  Redis (очередь)  │           │
│  └───────▲────────┘          └─────────▲─────────┘           │
│          │                             │                      │
│  ┌───────┴─────────────────────────────┴────────────────────┐ │
│  │  worker: истечения, сбор трафика, reconcile, CRL,        │ │
│  │          обработка вебхуков, outbox уведомлений          │ │
│  └────────────────────────────┬─────────────────────────────┘ │
│                               │  NodeDriver                    │
│  ┌────────────────────────────▼─────────────────────────────┐ │
│  │  ocserv (Docker)                                          │ │
│  │   occtl · PKI/easy-rsa · config-per-user                  │ │
│  │   connect-script · disconnect-script                      │ │
│  └───────────────────────────────────────────────────────────┘ │
│                                                               │
│  bot (aiogram): уведомления клиентам + алерты админу          │
└───────────────────────────────────────────────────────────────┘
```

### 4.1. Модули и границы

| Модуль | Отвечает за | Не знает про |
|---|---|---|
| `billing` | тарифы, платежи, вебхуки провайдеров, идемпотентность | ocserv, сертификаты, occtl |
| `subscriptions` | состояние подписки, срок, квоты, переходы статусов | как выдаётся ключ, кто заплатил |
| `provisioning` | выпуск/отзыв `.p12`, `config-per-user`, CRL, устройства | деньги, тарифы, Telegram |
| `nodes` | `NodeDriver`, статус, сессии, логи, сбор трафика | подписки, платежи |
| `notifications` | шаблоны, i18n, доставка в Telegram | всё остальное |
| `admin` | админ-API и UI | детали реализации ocserv (только через `nodes`) |
| `tma` | Mini App API, валидация `initData` | PKI, occtl |

**Публичная и админская части — два отдельных процесса**, а не один с разными префиксами.
Публичный `api-public` доступен через прокси и содержит только `/tma`, `/webhooks` и
`/internal`. Админский `api-admin` слушает `127.0.0.1:8080` и в прокси не заведён вообще —
ошибка в конфигурации прокси не может случайно открыть админку наружу. Оба процесса
используют общие модули и общую БД.

Модули общаются **доменными событиями** (`SubscriptionActivated`, `SubscriptionExpired`,
`SubscriptionRenewed`, `DeviceIssued`, `DeviceRevoked`, `TrafficThresholdReached`), а не
прямыми вызовами. Это то, что позволит вынести `nodes` в отдельный агент и подменить Tribute,
не трогая остальной код.

Проверка границ: `billing` должен собираться и тестироваться без единого импорта из
`provisioning` и `nodes`. Если это перестало быть правдой — граница нарушена.

### 4.2. `NodeDriver`

Абстракция над способом управления нодой. Единственная реализация сейчас —
`LocalDockerDriver` (`docker exec` в контейнер ocserv, работа с PKI на смонтированном томе).
Мультинодовость на этапе 4 добавляется как `RemoteAgentDriver` без изменений в доменном коде.

Интерфейс: `status()`, `list_sessions()`, `list_users()`, `disconnect_user(username)`,
`reload()`, `write_user_config(username, config)`, `remove_user_config(username)`,
`publish_allowlist(entries)`, `publish_crl(pem)`, `stream_logs()`.

### 4.3. Инвариант согласованности

**Источник истины о праве доступа — таблица `subscriptions` в Postgres.** Состояние ocserv
(содержимое `allowed.list`, CRL, файлы `config-per-user`) — производная, которую воркер
приводит в соответствие reconcile-циклом раз в 5 минут.

Следствия: пересоздали контейнер ocserv — состояние восстановится само; кто-то правил конфиг
руками — вернётся к нужному; после падения ноды ручной ремонт не требуется. Все расхождения
чинятся автоматически и пишутся в `audit_log` как действия актора `system`.

### 4.4. Разрешение конфликта портов

Камуфляж ocserv требует, чтобы сервер слушал 443/TCP и выглядел обычным сайтом. TMA тоже
требует публичный HTTPS. На одном IP оба на 443 не помещаются.

**Решение:** `nginx stream` с `ssl_preread` слушает 443 и маршрутизирует по SNI —
`vpn.example.com` в ocserv, `app.example.com` в HTTP-прокси панели. Коробка остаётся
однохостовой, оба домена работают на стандартном порту.

Серверный сертификат для `vpn.example.com` — настоящий Let's Encrypt. С самоподписанным
камуфляж не работает: домен обязан выглядеть как живой сайт.

## 5. Модель данных

Ключевое решение: **одно устройство = один сертификат = один ocserv-username**. При cert-auth
ocserv берёт username из CN сертификата, поэтому CN вида `c42-d3` бесплатно даёт пер-девайсную
статистику, штучный отзыв через CRL и честный подсчёт устройств в тарифе.

```
admins           username, password_hash, role, totp_secret, last_login

clients          telegram_id UNIQUE, username, first_name, lang,
                 trial_used_at, is_blocked, created_at

plans            code, name_i18n JSONB, description_i18n JSONB,
                 duration_days, device_limit, traffic_limit_bytes,
                 speed_limit_kbps NULL, price_amount, currency,
                 provider_product_ids JSONB, is_active, sort_order

subscriptions    client_id, plan_id, status, started_at, expires_at,
                 traffic_used_bytes, traffic_period_start,
                 provider, external_subscription_id, auto_renew,
                 created_at, updated_at

devices          subscription_id, name, platform, ocserv_username UNIQUE,
                 cert_serial, cert_fingerprint, issued_at, cert_expires_at,
                 revoked_at, revocation_reason, last_seen_at

payments         client_id, subscription_id NULL, provider, external_id,
                 amount, currency, status, raw_payload JSONB,
                 received_at, processed_at,
                 UNIQUE(provider, external_id)

webhook_events   provider, external_event_id UNIQUE, signature_ok,
                 payload JSONB, status, attempts, last_error, received_at

nodes            name, driver, config JSONB, public_host, status,
                 last_seen_at, is_active

traffic_samples  device_id, node_id, ts, bytes_in_delta, bytes_out_delta,
                 duration_sec              -- ретеншн 90 дней

traffic_daily    PK(device_id, day), bytes_in, bytes_out, duration_sec
                                           -- хранится бессрочно

session_log      device_id, node_id, started_at, ended_at,
                 client_ip, vpn_ip, bytes_in, bytes_out

revocations      cert_serial, device_id, revoked_at, applied_at

audit_log        actor_type(admin|system|client), actor_id, action,
                 target_type, target_id, details JSONB, ip, created_at

outbox           recipient_type, recipient_id, template_key, payload JSONB,
                 lang, status, attempts, send_after, sent_at, last_error

settings         key, value JSONB
```

**`.env` против `settings`.** В `.env` живёт только то, что нужно для старта процесса и что
опасно держать в БД: строки подключения к Postgres и Redis, `SECRET_KEY`, токен бота, ключи
API платёжных провайдеров, имя контейнера ocserv и пути. Всё остальное — trial, интервалы
сбора и reconcile, шаблоны, язык по умолчанию, пороги алертов — в `settings`, редактируется
из админки без перезапуска. Пересечения между ними нет, поэтому вопрос «что перевешивает»
не возникает.

Три таблицы несут бо́льшую часть надёжности системы.

**`webhook_events`.** Вебхук сначала сохраняется сырым и получает `200`, обработка идёт
отдельно из воркера. Tribute ретраит с экспоненциальным backoff около 24 часов; без этой
развязки любой баг в бизнес-логике превращается в шторм повторов и двойные активации.
`external_event_id UNIQUE` режет дубликаты на входе, `UNIQUE(provider, external_id)` в
`payments` — второй барьер.

**`revocations`.** Отзыв не применяется к ocserv немедленно, а кладётся в очередь. Воркер раз
в 30 секунд собирает накопившееся, перестраивает CRL одним проходом, делает `occtl reload` и
`occtl disconnect user` по каждому. Отзыв — редкое событие (потеря устройства, удаление
клиента), поэтому reload не мешает работе.

**`traffic_samples`.** Дельтовая модель из `ocserv-manager`: опрос `occtl show sessions all`
раз в 5 минут, считается прирост RX/TX. Известное слабое место — сессия, начавшаяся и
закончившаяся между опросами, теряется целиком. Закрывается хуком `disconnect-script`,
который отправляет финальные счётчики в `/internal/session-end`. Без него цифры для квот в
этапе 2 будут занижены, поэтому хук входит в этап 1.

## 6. Жизненный цикл подписки

```
                          ┌──────────────┐
      trial ─────────────►│              │◄──────── newSubscription
                          │    active    │
      renewedSubscription │              │  extends expires_at,
      ───────────────────►│              │  сбрасывает traffic_period,
                          └──┬────────┬──┘  БЕЗ перевыпуска сертификатов
                             │        │
              expires_at     │        │  traffic_used >= limit  (этап 2)
              достигнут      │        │
                             ▼        ▼
                        ┌─────────┐ ┌───────────┐
                        │ expired │ │ exhausted │
                        └────┬────┘ └─────┬─────┘
                             └──────┬─────┘
                                    ▼
                    удаление из allowed.list + occtl disconnect
```

Статусы: `pending_payment`, `trial`, `active`, `expired`, `exhausted`, `cancelled`, `blocked`.

**`cancelledSubscription` от Tribute не отключает доступ** — только ставит `auto_renew = false`.
Клиент оплатил период и дорабатывает его до `expires_at`. Обратное поведение — частая ошибка
в таких интеграциях, и она стоит возвратов и репутации.

**Продление** меняет одну строку в БД и одну строку в `allowed.list`. Клиент не делает ничего,
ключи не перевыпускаются, соединение не рвётся.

## 7. Выпуск ключей, PKI и контроль доступа

### 7.1. Механизм контроля доступа

У ocserv есть хук `connect-script`, который запускается на каждое подключение; **ненулевой код
возврата запрещает соединение**. Это основной рычаг контроля.

| Задача | Механизм |
|---|---|
| Проверка права на подключение | `connect-script` ищет username в `/var/lib/ocmanager/allowed.list` |
| Учёт трафика | `disconnect-script` шлёт финальные счётчики в `/internal/session-end` |
| Разрыв активных сессий | `occtl disconnect user <cn>` — мгновенно |
| Настоящий отзыв ключа | CRL, батчем раз в 30 секунд + `occtl reload` |

`allowed.list` пишется reconcile-циклом атомарно (запись во временный файл + `rename`) и
дополнительно сразу при смене статуса подписки. Скрипт не делает сетевых вызовов — VPN
продолжает работать даже при полностью лежащей панели, максимум с устаревшим на 5 минут
списком.

Это разводит срок действия сертификата (397 дней) и срок подписки. Продление не требует
перевыпуска; истечение не требует отзыва.

### 7.2. PKI

CA генерируется установщиком один раз. Приватный ключ — режим `0600` в отдельном volume;
в бэкапе он критичнее базы, поскольку его потеря означает перевыпуск всех ключей у всех
клиентов.

Клиентские сертификаты: `CN = c{client_id}-d{n}`, срок 397 дней. Ключ генерируется на сервере.
**`.p12` собирается на лету и не сохраняется на диск** — хранятся только сертификат, серийный
номер и отпечаток. Потерянный `.p12` не восстанавливается: выпускается новое устройство,
старое отзывается.

### 7.3. Флоу покупки в TMA

```
1. Клиент открывает Mini App        → валидация initData (HMAC по токену бота, TTL 5 мин)
2. Видит тарифы                      → i18n, цена, число устройств, ГБ, срок
3. Жмёт «Купить»                     → checkout-ссылка Tribute (или Stars invoice)
4. Оплата                            → провайдер шлёт webhook
5. webhook_events, ответ 200 сразу   → воркер: payment → subscription(active) → allowed.list
6. «Добавить устройство»             → выбор iOS / Android / Windows / macOS
7. Выпуск сертификата, сборка .p12 с одноразовым паролем
8. Выдача: одноразовая ссылка (TTL 15 минут, single-use token),
           пароль показан один раз, QR для перехода на телефон,
           пошаговая инструкция под выбранную ОС
9. Бот дублирует ссылку сообщением
```

**Trial:** один на `telegram_id` (поле `clients.trial_used_at`), одно устройство, тот же путь
без шага оплаты. Длительность и лимит трафика — настройки инсталляции
(`settings.trial_days`, `settings.trial_traffic_bytes`), значения по умолчанию 3 дня и 5 ГБ.
Технически trial — это обычная подписка на скрытом системном тарифе, а не отдельная ветка кода.

## 8. Платежи

Абстракция `PaymentProvider` с реализациями `TributeProvider`, `TelegramStarsProvider`,
`CryptoProvider`. Домен работает с событиями провайдер-агностично; специфика Tribute не
протекает в `subscriptions`.

**Tribute.** События: `newSubscription`, `renewedSubscription`, `cancelledSubscription`,
`newDigitalProduct`, `digitalProductRefund`, `newDonation`, `recurrentDonation`,
`cancelledDonation`. Подпись — заголовок `trbt-signature`, HMAC-SHA256 тела запроса ключом
API; сверка через `hmac.compare_digest`. Типы подписки: `regular`, `gift`, `trial`; при
продлении gift/trial следующая подписка становится `regular`. Ретраи с backoff около 24 часов.

**Риск.** Точная структура payload (наличие `telegram_user_id`, `expires_at`, `period`,
`amount`, `currency`) в публичной вики не раскрыта — там дана ссылка на OpenAPI-спеку.
Первая задача этапа 1 — принять реальный вебхук на тестовой подписке, зафиксировать payload
как фикстуру и построить маппинг на доменные события. До этого момента любые поля в коде —
предположение.

Идемпотентность обеспечивается на двух уровнях: `webhook_events.external_event_id UNIQUE` и
`payments UNIQUE(provider, external_id)`.

## 9. Админ-панель

Слушает `127.0.0.1`, наружу не публикуется; доступ по SSH-туннелю
(`ssh -N -L 8080:127.0.0.1:8080 user@host`). Логин с bcrypt-хешем, опционально TOTP.

| Раздел | Содержимое | Этап |
|---|---|---|
| **Обзор** | статус ноды, активные сессии, трафик за сутки, выручка за период, последние платежи, алерты | 1 (без выручки) / 2 |
| **Клиенты** | поиск по `telegram_id`/username; карточка: подписка, устройства, трафик, история сессий (IP, длительность, RX/TX), платежи, действия (заблокировать, продлить, выдать вручную) | 1 — таблицами; 2 — графики |
| **Статистика** | топ по трафику, суммарный график, распределение по тарифам, активные сессии в реальном времени, экспорт CSV | 2 |
| **Подписки** | фильтры по статусу, истекающие в ближайшие N дней, ручное продление | 1 |
| **Тарифы** | CRUD, привязка к продуктам Tribute/Stars, включение и отключение | 1 |
| **Платежи** | сверка с провайдерами, необработанные вебхуки, ручная переобработка | 1 — список; 2 — сверка |
| **Устройства** | все выпущенные сертификаты, отзыв, история подключений | 1 |
| **Нода** | статус, `occtl show status/users/sessions`, live-логи по SSE, start/stop/restart, состояние reconcile | 1 |
| **Аудит** | все действия `admin` / `system` / `client` | 1 |
| **Настройки** | токены, вебхуки, шаблоны уведомлений, язык, бэкапы | 1 — базовое; 3 — бэкапы |

Разделение простое: в этапе 1 всё, что нужно, чтобы **эксплуатировать** сервис — данные
доступны, но в виде таблиц и чисел. Графики, агрегаты и сверка платежей — этап 2. Сбор
трафика при этом идёт с первого дня, иначе на этапе 2 не будет истории для графиков.

Графики строятся из `traffic_daily` — предагрегата, а не `SUM()` по сырым сэмплам: иначе через
полгода админка встанет.

Управление нодой реализуется реестром разрешённых действий (приём из `openconnect-manager`) —
произвольная команда невозможна по построению. Интерактивный shell в веб не выводится.

## 10. Уведомления и i18n

Все исходящие сообщения проходят через таблицу `outbox` с ретраями — Telegram API отвечает
ошибками и лимитами, и терять уведомление об окончании подписки нельзя.

**Клиенту:** оплата принята, ключ выдан, до окончания N дней, подписка закончилась, израсходовано
80 % трафика, устройство отозвано.

**Админу:** нода недоступна, вебхук в dead-letter, новая оплата, подозрение на злоупотребление
(аномальный трафик, много устройств с одного IP), бэкап не выполнен.

**i18n** с первого дня: `ru`, `en`. Тексты в JSON-каталогах, язык клиента берётся из
`clients.lang` (по умолчанию из Telegram), язык админки — из настроек. Названия и описания
тарифов хранятся как JSONB со всеми локалями.

## 11. Безопасность

- Админка слушает только loopback; наружу публикуется исключительно TMA.
- Валидация `initData` Telegram Mini App: HMAC по токену бота, TTL 5 минут, защита от replay.
- Проверка подписи вебхуков через `hmac.compare_digest`, отказ при несовпадении с записью
  в `webhook_events(signature_ok = false)` и алертом.
- Rate-limit на TMA-эндпоинтах, особенно на выдаче устройств и trial.
- Все команды — `subprocess` со списком аргументов, без `shell=True`. Имена контейнера,
  compose-сервиса и systemd-юнита берутся только из конфига, никогда из запроса.
- Валидация всех идентификаторов, попадающих в имена файлов и CN, по строгим регуляркам.
- Одноразовые ссылки на `.p12`: TTL 15 минут, single-use, токен не переиспользуется.
- Приватный ключ CA — `0600`, отдельный volume, не покидает хост.
- Секреты в `.env`, генерация при установке; в репозитории только `.env.example`.
- Полный аудит: каждое действие админа, системы и клиента.
- Бэкапы: `pg_dump` + tar PKI, шифрование, ретеншн; проверка восстановления в чеклисте релиза.

## 12. Отказы и деградация

| Сбой | Поведение системы |
|---|---|
| Вебхук пришёл дважды | `UNIQUE(provider, external_id)` — второй игнорируется |
| Ошибка обработки вебхука | событие сохранено, ретраи с backoff, после N попыток dead-letter + алерт |
| Оплата прошла, выдача упала | подписка уже `active`, устройства выдаются лениво — клиент не теряет деньги |
| Нода недоступна | статус `degraded`, provisioning в очередь, применяется при возврате, алерт админу |
| ocserv пересоздан, конфиг правили руками | reconcile восстанавливает за ≤ 5 минут |
| Панель лежит | VPN работает: `connect-script` читает локальный `allowed.list` |
| Redis недоступен | API отвечает, фоновые задачи копятся, обрабатываются после возврата |
| Потеря CA | **невосстановимо без бэкапа** — автобэкап PKI обязателен, восстановление проверяется |

## 13. Тестирование

- **Юнит:** FSM подписок (все переходы, включая `cancelled` → доработка до `expires_at`),
  идемпотентность обработки вебхуков, расчёт дельт трафика с учётом обнуления счётчиков,
  генерация `allowed.list`.
- **Контрактные:** зафиксированные фикстуры реальных payload Tribute; тест ломается, если
  маппинг перестал соответствовать.
- **Интеграционные:** в compose поднимается настоящий ocserv; выпуск сертификата → подключение
  клиентом `openconnect` → проверка сессии в `occtl` → истечение подписки → проверка отказа
  в подключении. Это главный тест продукта: он проверяет ровно то, за что платит клиент.
- **Reconcile:** намеренно портим состояние ocserv (удаляем `allowed.list`, добавляем лишнего
  пользователя) и проверяем самовосстановление.
- **Нагрузочный (этап 2):** сбор трафика при 500 активных сессиях, время ответа админки на
  графиках за год.

## 14. Этапы

**Этап 1 — MVP: деньги → ключ.**
Приём вебхука Tribute с фиксацией реального payload; модель данных; FSM подписок; PKI и выпуск
`.p12`; `connect-script` и `disconnect-script`; `allowed.list`; reconcile-цикл; сбор трафика;
TMA (тарифы, покупка, устройства, инструкции); trial; тонкая админка (клиенты, устройства,
статус ноды, аудит); каркас i18n ru/en; алерты админу.

**Этап 2 — полная админка и биллинг.**
Статистика и графики, квоты трафика с принудительным отключением, криптоплатежи и Telegram
Stars, полный набор уведомлений клиентам, промокоды и реферальная механика, экспорт CSV.

**Этап 3 — коробка.**
Установщик, веб-визард первой настройки (домены, Let's Encrypt, камуфляж-токен, генерация CA,
первый админ), бэкапы и восстановление, документация для покупателя, процедура обновления.

**Этап 4 — мультинодовость.**
`RemoteAgentDriver`, агент на ноде, выбор локации в TMA, health-чеки и переключение,
распределение клиентов по нодам.

Каждый этап получает отдельную спецификацию и отдельный план реализации.

## 15. Открытые вопросы и риски

| # | Вопрос / риск | Как закрываем |
|---|---|---|
| 1 | Структура payload вебхуков Tribute не подтверждена | Первая задача этапа 1 — принять реальный вебхук, зафиксировать фикстуру |
| 2 | Привязка платежа Tribute к `telegram_id` клиента | Если в payload нет `telegram_id` — использовать `payload`/`external_id` из checkout-ссылки, формируемой TMA |
| 3 | UX импорта `.p12` на iOS требует установки профиля | Проверить на реальном устройстве в этапе 1; при неприемлемом UX рассмотреть добавление парольной авторизации как альтернативы |
| 4 | Точность учёта трафика при обрыве связи с нодой | Хук `disconnect-script` + сверка с `occtl` при reconcile; допустимая погрешность фиксируется тестом |
| 5 | Риск блокировки платёжного провайдера за VPN-тематику | Абстракция `PaymentProvider` позволяет заменить провайдера без изменения домена |
| 6 | Юридический статус деятельности | Вне области задач; решается владельцем инсталляции |
