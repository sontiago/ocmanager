# Этап 3: «коробка» — установка одной командой, бэкапы, обновление

Дата: 2026-10-23. Продолжает §14 спеки `2026-09-02-ocmanager-saas-design.md` («Этап 3 — коробка»).
Текущий порядок установки по README (`deploy/README.md`) становится диалогом.

## Зачем

Покупатель с базовыми знаниями Linux должен пройти путь «чистый сервер → первый подключённый клиент» без
правки `.env` руками и без знания порядка запуска, а потом не бояться потерять данные и обновляться.

## Как это доставляется (решение владельца)

Продукт лежит в GitHub. Покупатель клонирует репозиторий (доступ — на его стороне: deploy key или токен) и
запускает установщик из корня клона. Образы собираются на его сервере, как сейчас. Релизов, реестра образов и
скачивания «одной ссылкой» нет.

```bash
git clone <репозиторий> ocmanager && cd ocmanager
sudo ./install.sh
```

## Цели

- Одна команда ставит продукт целиком; всё нужное установщик спрашивает по ходу.
- Установщик можно безопасно запускать повторно и продолжать после сбоя с того же места.
- Бэкапы по расписанию из коробки: база, CA и `.env`, шифрованные, с хранением и алертом админу при сбое.
- Восстановление и обновление — одной командой каждое, с копией перед обновлением и откатом.
- Русская инструкция для покупателя, по которой всё это можно сделать без нас.

## Не цели

Веб-мастер настройки (заменён терминальным), образы в реестре и релизы, мультинод, установка не на Debian/Ubuntu,
GUI для бэкапов, автоматическое продление и биллинг самого продукта.

## Анти-цели

- Установщик не должен молча делать то, о чём не спросил: ничего не ставится в систему сверх Docker (по
  согласию) и не меняется существующий firewall.
- Секреты не печатаются в лог и не попадают в историю команд; `.env` — 0600.
- Бэкап с приватным ключом CA никогда не хранится незашифрованным.

## Решения (мои, кроме отмеченных выше; проверьте при чтении)

1. **Язык.** `install.sh` — тонкая обёртка: проверяет `python3` (есть в Debian 12 и Ubuntu 22.04) и запускает
   `deploy/installer/install.py`. Логика на Python (только стандартная библиотека): её можно покрыть тестами с
   подменой команд, сети и DNS, чего не сделать в bash. Интерфейс мастера — русский.
2. **Что проверяет мастер до установки.** Debian 12+/Ubuntu 22.04+; root; память (меньше 2 ГБ и нет swap —
   предложит создать 2 ГБ swap); свободные 80/tcp, 443/tcp, 443/udp; Docker 24+ с Compose v2 (нет — предложит
   установить из репозитория дистрибутива); для обоих доменов A-запись совпадает с публичным IP сервера (IP
   определяется внешним запросом; при несовпадении — объяснение и возможность продолжить на свой риск).
3. **Что спрашивает.** Домен Mini App; домен VPN; почта для Let's Encrypt; токен бота (мастер проверяет его
   запросом `getMe` к Telegram и сам берёт `OCM_BOT_USERNAME`); логин и пароль первого админа (скрытый ввод,
   ≥ 12 символов, либо сгенерировать и показать один раз); ключ Tribute (можно пропустить); куда копировать
   бэкапы (необязательно, `user@host:/путь`). Всё остальное генерируется: пароли Postgres и Redis (hex), ключ
   приложения, внутренний токен, камуфляжный секрет.
4. **Порядок установки** — как в README: `.env` → `docker compose build` → базы и миграции → `pki init` → админ →
   остальные сервисы → ожидание обоих сертификатов → `doctor.sh` → итог. Прогресс пишется в файл состояния
   (`deploy/.install-state`), повторный запуск пропускает сделанное. `.env` существует — мастер спрашивает:
   использовать как есть или пройти вопросы заново (старый сохраняется как `.env.bak`).
5. **Итоговый экран:** адреса, команда SSH-туннеля к админке, что сделать в @BotFather (Edit Web App URL), как
   узнать свой chat id для алертов (`/whoami` и `ocm admin-chat <число>`), где лежит ключ шифрования бэкапов и
   предупреждение «сохраните его отдельно от сервера».
6. **Команда `ocm`.** Установщик кладёт `/usr/local/bin/ocm` (скрипт-обёртка над compose в каталоге установки):
   `status` (= doctor), `logs [сервис]`, `backup`, `restore <файл>`, `update`, `rollback`, `admin-chat <id>`,
   `admin-password`.
7. **Бэкап.** Один файл `ocmanager-<дата>.tar.gz.enc`: `pg_dump` базы, том `pki` (CA), `.env`. Шифрование —
   `openssl enc -aes-256-cbc -pbkdf2` с ключом из `/root/.ocmanager-backup-key` (0600, создаётся установщиком;
   показывается один раз). Каталог `/var/backups/ocmanager`, хранится 14 последних. Расписание — systemd timer
   раз в сутки (03:30). Необязательное копирование на другой сервер через `rsync`/`scp`. Сбой любого шага
   → алерт админу в Telegram (шаблон `backup_failed`, ставится через CLI в очередь, воркер отправляет); успех
   пишет метку времени, а `doctor.sh` краснеет, если последний успешный бэкап старше 36 часов.
8. **Восстановление** (`ocm restore <файл>`): запрашивает подтверждение с предупреждением «заменит данные»,
   останавливает сервисы, расшифровывает, возвращает базу, `pki` и (по запросу) `.env`, поднимает, запускает
   `doctor`. Перед восстановлением снимает аварийную копию текущего состояния.
9. **Обновление** (`ocm update`): бэкап → `git pull --ff-only` → `compose build` → `up -d` (миграции накатываются
   сервисом `migrate`) → `doctor`. Не сошлось — стоп без побочных действий. После неудачного `doctor` печатает
   `ocm rollback`: возврат на прежний коммит, пересборка и (после подтверждения) восстановление базы из копии,
   снятой перед обновлением.
10. **Проверка без сервера.** Тесты логики установщика и бэкапов идут в CI с подменой команд (`docker`,
    `systemctl`, `openssl`, сеть, DNS). Сквозная проверка на живом сервере — ручной чек-лист (доменов и Let's
    Encrypt в CI нет). Мастер поддерживает `--answers файл.json` и `--dry-run` (показать, что будет сделано), на
    них же строятся тесты.

## Остаётся исполнителю

Тексты вопросов и сообщений, раскладка файлов внутри `deploy/installer/`, детали проверок Docker и swap,
формат файла состояния, имена юнитов systemd.

## Критерии готовности

- Установщик на чистой Debian 12 / Ubuntu 22.04 (ручной прогон по чек-листу) доводит до зелёного `doctor` и
  работающей админки, повторный запуск ничего не ломает.
- `ocm backup` создаёт шифрованный файл; `ocm restore` на другом чистом сервере возвращает базу и CA, выданные
  ключи клиентов продолжают работать.
- `ocm update` и `ocm rollback` работают на тестовом обновлении.
- Бэкап-сбой даёт алерт; `doctor` замечает устаревший бэкап.
- Тесты логики зелёные в CI; `shellcheck` на `install.sh` и `ocm` без замечаний.
- `deploy/README.md` заменён русской инструкцией покупателя (установка, бэкап, восстановление, обновление,
  «если что-то не так»).
